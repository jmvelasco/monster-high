## Context

Character stories are generated by `GroqStoryGenerator` using the Groq API with `llama-3.1-8b-instant`. The current configuration sets `max_tokens: 400`, which is insufficient for Spanish-language narratives of 5-6 sentences. When the token limit is reached, the API truncates the response mid-sentence. The prompt does not instruct the model to prioritize narrative closure.

The change is scoped to two files in the infrastructure and config layers of the backend:
- `apps/backend/src/config/config.ts` — token budget
- `apps/backend/src/infrastructure/story-generator/GroqStoryGenerator.ts` — prompt template

## Goals / Non-Goals

**Goals:**
- Stories always end with a complete sentence and narrative closure.
- Token budget is large enough to accommodate Spanish-language stories of 5-6 sentences.

**Non-Goals:**
- Changing the AI model.
- Adding runtime truncation detection or retry logic.
- Modifying the frontend rendering.
- Regenerating existing stored data.

## Decisions

### D1: Increase `maxTokens` from 400 to 1024

**Rationale:** 5-6 sentences in Spanish typically require 350-600 tokens. Setting 1024 provides comfortable headroom without being wasteful. The prompt already constrains length to 5-6 sentences, so the model self-limits output well below 1024 in most cases.

**Alternatives considered:**
- **600 tokens**: Still tight for edge cases with longer character data. Too close to the boundary.
- **2048 tokens**: Unnecessary overhead. The prompt constrains length, so extra budget is wasted.

### D2: Add explicit closure instructions to the system prompt

**Rationale:** Even with more tokens, `llama-3.1-8b-instant` benefits from explicit instructions about story structure. Adding rules about narrative closure makes the model plan for an ending from the start.

**Changes to prompt:**
- Add instruction: the story MUST end with a complete closing sentence.
- Add instruction: prioritize finishing the story over including every detail.
- Keep existing constraints (5-6 sentences, Spanish from Spain, no sections).

**Alternatives considered:**
- **System message role**: Groq supports `system` role messages. However, the current prompt uses a single `user` message and works well otherwise. Splitting into system + user adds complexity for marginal benefit in this context.

### D3: Keep changes in infrastructure layer only

**Rationale:** Following hexagonal architecture, the prompt template and token config are infrastructure concerns. The domain port `CharacterStoryGenerator` contract (`generateStory(character): Promise<string>`) does not change. No domain or application layer changes are needed.

## Risks / Trade-offs

- **[Higher token consumption]** → Each request may consume up to 2.5× more tokens. Mitigation: the prompt still limits output to 5-6 sentences, so actual consumption increase is marginal. Monitor Groq API usage after deployment.
- **[Model may still occasionally truncate]** → At 1024 tokens the risk is very low for 5-6 sentences, but not zero. Mitigation: the prompt now explicitly instructs closure, and 1024 tokens is ~500 words in Spanish — far more than needed for 5-6 sentences.
- **[Prompt changes may shift story tone]** → Adding structural instructions could make stories slightly more formulaic. Mitigation: only add closure instructions, do not change the creative direction or tone constraints.
